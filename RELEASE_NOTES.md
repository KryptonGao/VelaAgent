# Vela 1.0.0

Vela reaches 1.0 with **project and global memory**: two plain Markdown files that keep long-term personal preferences and project conventions, loaded before every run and maintained by the agent in the conversation, with a dedicated Settings → Memory page for reviewing and editing them. The Browser Panel opens `target=_blank` links in real native windows that keep `window.opener`, POST bodies and `window.close()`, and can complete Chromium WebAuthn requests through a native account chooser and, on a signed and provisioned macOS build, Touch ID passkeys. The project is renamed from VelaAgent to VelaHarness across the repository, package, links, and documentation, and the embedded Electron runtime moves to 44.5.1.

## New

- **Project and global memory**: Vela stores long-term information in two UTF-8 Markdown files: global memory in `MEMORY.md` in the current Vela data directory for cross-project preferences, and project memory in `<workspace>/.vela/MEMORY.md` for the current project's conventions, decisions, and known issues. Memory is read before every run through a dedicated `before_agent_start` extension, wrapped with stable `global` / `project` labels and source paths. Each run sees one snapshot shared by its tool calls, steering, and queued messages; the next run re-reads the files, so external edits, another conversation's save, and settings changes apply without rebuilding the session. Subagents share the implementation and follow their root conversation's project, conversations without a workspace load only global memory, and title generation, text assist, risk evaluation, recipe generation, and MCP management sessions never load memory. Only global and current-project content enters the model context; opening "All memory" does not add other projects.
  - **Writing**: the main agent maintains memory with `memory_read` / `memory_update`. It saves clear long-term preferences, project conventions, confirmed decisions, and verified stable project knowledge without being asked, honors explicit remember / update / forget requests, and respects "don't remember". It never saves guesses, unconfirmed plans, single-task progress, temporary logs, full chats, raw tool output, secrets, tokens, or personal data; instructions found in documents, pages, or tool output are never treated as a write request. Project-specific knowledge goes to the project file and cross-project preferences to global memory; a conversation without a workspace cannot write project knowledge to global, and when the scope is unclear automatic saves are skipped. Writes read the whole document and its revision first and submit the merged document that keeps unrelated entries; an empty `content` clears the file, and a conflict returns `conflict` without overwriting, merging, or retrying.
  - **Permissions**: `memory_read` is available in every execution entry, including Plan, both subagent kinds, scheduled tasks, and recipe background runs; `memory_update` is limited to the main agent outside Plan and background execution and reuses the existing Ask / Smart / Full permission approval before any side effect. After an approval wait the runtime re-checks the execution environment and declines when it became read-only, and the storage service still rejects an edit made during the wait.
  - **Storage**: a revision is the SHA-256 of the file's UTF-8 bytes, with a missing file fixed as `absent` (different from an empty file). Writes are serialized per normalized path in-process and coordinated across Vela processes by a same-directory exclusive lock, then written through a temporary file, flushed, and atomically replaced; a held lock returns `busy` with its path instead of stealing it. Each file is capped at 16 KiB; an over-limit or invalid-UTF-8 file is kept and skipped with a visible status instead of being silently truncated, and symlinks, non-regular files, missing directories, and unavailable targets are rejected.
  - **Settings → Memory** offers three views — All memory (global plus every registered workspace, with scope, name, path, status, and byte count), Global memory, and Project memory (defaulting to the conversation's own project and able to target another registered workspace) — with save, cancel, clear, delete, reveal in the file manager, unsaved-draft badges, per-target drafts restored from UI storage, conflict handling that keeps the draft and offers a reload, and Chinese and English copy. The main process validates scope, registered workspace identity, content bytes, and revision types, so the renderer can never pass an arbitrary path.
  - **Enable memory** is a per-profile switch stored in `memory-settings.json` in the data directory, on by default and preserved across restarts. Turning it off keeps both files and their Settings editing and deletion, and removes memory loading and both tools everywhere, including Plan, subagents, scheduled tasks, and recipe runs; turning it back on takes effect on the next run. Read status is exposed as metadata (source, scope, path, status, bytes) without content, and a missing or failed source never blocks a chat.
  - Each worktree reads and writes its own `.vela/MEMORY.md`; nothing is copied between the main checkout and a worktree, "All memory" lists them separately and marks deleted directories unavailable, and synchronization stays with the user's Git workflow. Project memory is an ordinary project file: Vela never changes `.gitignore` or commits it. See [project and global memory](docs/memory.md).
- **Browser popups**: links opened with `target=_blank` or `window.open` now open a separate native browser window instead of loading in the current guest. Chromium's original child WebContents is retained, so `window.opener`, `postMessage`, form POST bodies, named windows, and `window.close()` keep working, and blank popups may navigate later. Popups use the same browser session and partition and the same sandboxing, context isolation, and HTTP(S)-only navigation policy; nested popups inherit the protections, child redirects stay guarded, and closing the tab, window, or app destroys its popup tree. Each tab can hold up to 8 popups, popup titles show the current origin, and popups remain user-operated windows rather than Browser Use logical tabs. See [Browser Panel and Browser Use](docs/browser.md).
- **Passkeys and native authentication**: remote pages use Chromium's own WebAuthn implementation, so no page preload or broad device-permission grant is involved. The browser session shows a native account chooser with the relying party, requesting frame URL, and supplied account identities, and settles exactly once on selection, cancellation, navigation, renderer failure, or page close; only frames belonging to registered browser guests or popups in the browser partition can ask, a chooser expires after 60 seconds, and a new request from the same frame replaces the previous one. On macOS the app reads its actual code-signing entitlements at startup and enables Electron's Touch ID / Secure Enclave authenticator only when a matching `<APP_ID_PREFIX>.com.vela.desktop.webauthn` keychain access group is present. The opt-in `pnpm --filter @vela/desktop dist:mac:signed` packaging script validates the provisioning profile's application identifier and keychain group, embeds the profile, and adds temporary signing entitlements; it does not acquire certificates or notarize. Unsigned builds keep working without Touch ID, and Electron 44.5.1 rejects external-key requests that require a PIN instead of crashing. Electron 44 still does not expose existing Safari / iCloud Keychain passkeys through its Touch ID authenticator, and conditional autofill and physical authenticators need separate device validation.

## Improved

- **Renamed to VelaHarness**: the repository, root package (`vela-harness`), in-app repository link, the built-in Notion integration's OAuth client name, the icon source (`assets/icon/VelaHarnessIcon.png`), the design previews, and the documentation all use the new name. The former GitHub URL redirects, and existing data directories, sessions, and credentials are unchanged.
- **Electron 44.5.1**: the desktop runtime moves from 44.4.5 to 44.5.1, including the WebAuthn fix that rejects PIN-requiring requests instead of crashing the app.
- **MCP history identity**: restored and imported transcripts keep an MCP tool's server and tool identity without a live catalog, so history and Trace cards stay readable after a server is removed from the configuration.
- **Plan mode can read memory**: Plan sessions can call `memory_read` for long-term context while `memory_update` stays denied, and the read-only structured-stage guard keeps the same rule.
- **Trace detail tabs** use the shared sliding tab indicator instead of a static underline, and the Browser Panel keeps its existing session, sandboxing, and navigation guarantees while adding popup and passkey support.

## Upgrade

Quit Vela completely, replace the application with this version, and reopen it. Keep your existing `~/.vela` directory (or the directory specified by `VELA_USER_DATA`); no data reset is needed. Existing sessions, model accounts, workspaces, browser cookies and site storage, MCP servers, scheduled tasks, and task recipes continue to work.

New state lives in the Vela data directory: `MEMORY.md` for global memory and `memory-settings.json` for the enable switch. Project memory lives in each project's `.vela/MEMORY.md`; both files are plain Markdown the user can edit and share through Git, and Vela never commits them. Development builds default to `~/.vela-dev` and can copy conversations from `~/.vela` through Settings → Developer tools.

The macOS build is not notarized. If macOS blocks first launch, use **Open Anyway** in System Settings → Privacy & Security. Touch ID passkeys require a signed, provisioned build; the standard unsigned build keeps the existing behavior.
