# Vela 0.1.7

This release adds **Task Recipes**: save a parameterized task template once, fill in its parameters, review the preview, and start it in a new conversation in the workspace you choose. Recipes cover built-in examples, AI-organized drafts, personal, project and team libraries, import and export, Skill dependencies, scheduled bindings, standalone worktrees, structured stages with conditions, approvals and controlled retries, and local run history and comparisons. Development builds also get a separate `~/.vela-dev` profile with one-way conversation sync from the installed app.

## New

- **Task recipes**: the sidebar's **Task Recipes / 任务配方** entry opens a dedicated page where recipes can be created, edited, duplicated, filtered, searched, exported, and deleted, with per-recipe usage history. `/` in the composer opens one grouped menu of **Skills** and **Task recipes**, searchable by name, description, or tags and navigable with the arrow keys, Enter/Tab, or the pointer; choosing a recipe removes the slash query, keeps the rest of the chat draft, and opens its parameter form instead of sending immediately. Running chats do not offer recipe options. Three built-in examples ship in Chinese and English — **Fix a bug** (Agent), **Review changes** (Plan), and **Prepare a release** (Agent) — with read-only templates that can be copied into personal recipes.
  - A recipe stores its goal, parameters, workflow requirements, deliverables, default mode, tags, and optional source reference. Parameters support text, multiline, select, boolean, and path types with labels, help, required flags, defaults, and options. Templates use `{{parameter_id}}`, `{{workspace.name}}`, and `{{workspace.path}}` and provide an insert-at-cursor entry; unknown or incomplete placeholders and invalid defaults block saving, and removing an in-use parameter requires fixing its references first.
  - Recipes can start from a blank template, a copy, a user or assistant text message (the selected text when present, otherwise the message text) through the chat header's **More chat actions** menu, or a Plan Document revision through **Create recipe** in the plan pane. Source references carry the conversation, message, or plan ID without copying other messages, images, tool results, or hidden thinking.
  - **Preview and start**: the use form pins the recipe revision, accepts an existing local workspace or a managed worktree, and allows per-run overrides for mode, model, reasoning effort, and execution permissions plus extra instructions. Overridden permissions apply to the new chat and its subagents only and never change the app defaults; the composer shows the chat's fixed permission snapshot and disables changing it there. The main process re-checks paths, the model, Skill resolution, and the Git scope and compares the preview fingerprint before starting, and re-queries Git changes every two seconds; when the directory, path objects, Git HEAD/range/working tree, or resolved settings changed, the start is blocked and the preview refreshes. Parameters, directory, and settings typed during validation are never silently rewritten. Plan recipes keep the existing read-only limits and still need the Plan Document approval before implementation. The recipe body is submitted as an ordinary user message and cannot raise instruction priority or grant new tool authorization.
  - **Runs and snapshots**: every save that changes content increments the revision; each run stores the full template snapshot, parameter values, extra instructions, expanded prompt, real directory, mode, model, reasoning effort, permissions, and Git SHA, so editing or deleting a recipe never rewrites history. Run status is `starting`, `running`, `waiting_for_user`, `responded`, `failed`, `stopped`, or `interrupted`; `responded` means a reply was generated and is not task acceptance. Each launch request has a stable requestId; records and a reserved conversation ID are persisted atomically before the conversation, binding, and send intent are written, so duplicate requests never create a second chat, and a missing send intent means nothing was submitted. Restart marks unfinished runs as interrupted and never replays them; a session JSONL written without its index or binding entry is reconciled to the reserved ID without running the model. History pages through runs 20 at a time and keeps deleted recipes viewable.
  - User recipes and run records live in `task-recipes.json` in the Vela data directory (following `VELA_USER_DATA`), independent of model credentials, written serially through a temporary file and atomic rename with fsync at key steps; a corrupt or unknown-version file stops writes and keeps the original file.
- **Structured stages**: a recipe can define up to 20 stages with stable IDs, names, instructions, side-effect scopes, approval-before-entry flags, and retry limits; stage instructions share the parameter placeholders and count toward the combined 40,000-character limit with the template body. In Agent mode the runtime submits selected stages sequentially in the same new conversation, persisting each attempt's send intent before invoking the existing runtime. Stage states are pending, skipped, waiting for approval, running, responded, failed, stopped, or interrupted. Response status comes from the real `prompt_end` and tool evidence from `tool_end`; evidence links to persisted session entries or tool-call IDs and is checked for ownership by the main process. Recipes without stages keep the single-submission behavior, and Plan recipes only plan and never start the stage state machine or auto-approve.
- **Stage conditions, approvals, and controlled retries**: conditions compare fixed parameter values only, with typed equals/not-equals operators; no expressions, Shell, or model decisions are involved, and missing values are never guessed. The preview lists stages that will run and be skipped, and Agent mode blocks starting when conditions select no stage. Approval waits before entering a stage; approval submits it, rejection stops all later stages, and the decision is stored. The stage dock above the composer shows the current stage action even before the first chat message, and free chat, mode changes, or model changes cannot bypass a pending stage boundary. Read-only stages reuse Plan's read-only guards (reading, restricted Shell, and questions only; no file changes, browser, MCP, or subagents), and every structured stage runs in the root session. SDK automatic error retries and auto-compaction are disabled for structured invocations and restored afterward; a configured retry limit (0–3) applies only to confirmed failures of read-only stages, re-checks the directory, paths, Skills, Git, and model, and uses a fresh requestId so duplicate retries cannot create a second attempt. Exceptions, uncertain results, stops, interruptions, workspace mutations, and external-service stages are never retried in place, and scheduled failures must be recreated as a new task from the snapshot.
- **Project libraries, import and export**: recipes can be saved to a personal library or to an existing project's `.vela/task-recipes.json` (schema version 1, at most 100 recipes). Project files carry a UUID and revision per recipe, can be copied with the project, and get an independent identity per real project directory, so duplicate names across projects never overwrite each other. A corrupt, unknown-version, oversized, or symlinked file is rejected for that project without affecting the personal library. **Import recipes** and **Export** use an exchange JSON (`format: "vela-task-recipes"`, schema version 1, up to 4 MB and 100 recipes) that contains templates only — no run history, model, permission, source-chat references, or built-in Git privileges. Import validates the whole file first, shows an unsaved review list, and saves each item under a new ID and revision 1 with explicit review of its text and Skill names; duplicate names are not overwritten, and an exported built-in imports as a normal custom recipe.
- **Skill dependencies**: recipes declare up to 20 unique required Skill names (one per line). Previews and start resolve them against the target workspace's existing Skill directories and list missing, disabled, or unreadable entries and block starting; Vela never downloads, enables, or changes permissions for them. The context records each resolved location and content fingerprint, and changing a Skill while a preview is waiting invalidates it. Snapshots do not freeze Skill files.
- **Scheduled bindings**: after parameters and the full preview are valid, **Schedule recipe** saves the recipe snapshot, fixed parameter values, extra instructions, mode, and launch settings as a scheduled task binding. The version policy defaults to **pin this version** and can explicitly follow the latest version at each run; a pinned version keeps working after the template changes or is deleted, while following the latest reads the newest template, fills new parameter defaults, and re-validates before running — a deleted, parameter-incompatible, or Skill-unavailable run fails that occurrence instead of guessing. Bindings reuse the existing schedule, timezone, missed-run, concurrency, and restart-interruption policies, hold the original scheduler lock while a run waits for approval, write both a scheduler record and a recipe run record, and create their background chat without switching the current chat or workspace. The Scheduled tasks page shows the bound snapshot and parameters and can change the schedule time or version policy, pause, or delete a task. Parameter changes require a new binding, and a bound task's prompt is read-only in the task editor. Bindings use an existing workspace and never create a worktree automatically.
- **Standalone worktree**: a manual launch can opt into **Create an isolated worktree** with an explicit start commit or ref, a new branch, and no uncommitted or untracked files carried over. The preview shows the resolved SHA and the managed target directory, and path parameters are checked against objects at the start commit; symlinks are rejected. Vela persists the directory, branch, and SHA reservation before reusing the existing worktree manager, so the same requestId cannot create a second worktree, and a creation or later pre-check failure keeps a reviewable record and any created directory instead of submitting to the model. New directories are re-checked for paths, Skills, HEAD, and uncommitted files. Cleanup in the run history requires explicit confirmation and refuses uncommitted files or running tasks; it removes only the managed directory and keeps the branch, chat, and records. Worktrees are never removed automatically on completion, failure, or interruption.
- **Team libraries and comparisons**: **Team recipe libraries** connects an existing project, defaults to local read-only, and requires an explicit write opt-in; saving writes only on an explicit save action to the project's `.vela/team-task-recipes.json` (schema version 1, up to 100 recipes and 4 MB) exchanged through Git or shared folders, with no new cloud service or account. Template text, stages, Skill names, and parameter defaults are shared; source-chat references, launch settings, run inputs, records, and ratings are not. Template UUIDs stay portable while app identity is per real directory, revision checks and content fingerprints reject conflicting or identical-version external edits, an exclusive write lock prevents concurrent writes, and corrupt, unknown-version, or symlinked files are rejected without writing; a leftover `.lock` prompts manual inspection instead of being stolen. Disconnecting does not delete shared or local files.
  - Finished runs can be manually rated **accepted / needs improvement** with up to 2,000 characters of note; ratings are never inferred from reply text. Comparisons group by recipe identity and revision and show usage counts, generated replies, failed/stopped/interrupted counts, rating samples, and average duration (from first launch to final end, including approval and retry waits); cross-model, cross-workspace, and cross-difficulty comparisons are not controlled experiments, unanswered samples are not failures, and `responded` is not a success rate. Statistics and ratings stay local and are never uploaded.

## Improved

- Development builds now run as **Vela Dev** with their own `~/.vela-dev` data directory and separate Electron user data, session data, cache, and single-instance lock, so a source build and an installed `Vela.app` can run at the same time. Both keep separate accounts, conversations, settings, and scheduled tasks; `VELA_USER_DATA` still overrides the directory and reuses the default lock for that data directory instead of opening a second one. Settings → **Developer tools → Sync production conversations** (development builds only) copies new conversations from the installed app's `~/.vela`, including messages, plans, subagent history, traces, and file checkpoints; existing conversations are skipped, the source directory is treated as read-only, imported conversations appear in the sidebar immediately without changing the open chat, and unreadable history files are reported. See the README for the development profile.
- Chats created without an explicit workspace are now represented separately from their execution directory: they appear under **Recent** in the sidebar instead of workspace groups, hide their workspace label in the sidebar and search results, and hide the Version Control tab, and the workspace selection clears for them. A chat's execution directory can equal the default directory while still being an explicitly selected workspace, and switching workspaces preserves the conversation the user already selected. See [task recipes](docs/task-recipes.md).
- Tool approval and question requests now carry the calling conversation and an abort signal: cancelling or aborting a command or file write removes the pending approval instead of leaving it waiting, and both can mark a task recipe run as waiting for the user.
- Recipe conversations create their Pi session with the reserved conversation ID and fsync the header before any message is submitted, and the conversation index flushes strictly before importing snapshots; a conversation with a missing index or binding entry is reconciled on the next start.
- Scheduled tasks bound to a recipe show their binding snapshot including parameters, mode, instructions, and version policy; the task prompt is read-only while a binding exists, and its version policy can be switched between pinned and follow-latest in the task editor.
- Login shell PATH detection now runs in a detached session with shell session tracking disabled, so quitting Vela no longer disturbs the terminal it was launched from.
- A chat's previous error banner now clears as soon as its next turn starts streaming.
- Settings → Development tools joins the About/Appearance sections in both Chinese and English, and sidebar and conversation search hide workspace metadata for chats without a workspace.

## Upgrade

Quit Vela completely, replace the application with this version, and reopen it. Keep your existing `~/.vela` directory (or the directory specified by `VELA_USER_DATA`); no data reset is needed. Existing sessions, model accounts, workspaces, browser cookies, and site storage continue to work.

New state lives in the Vela data directory: `task-recipes.json` for personal recipes and run snapshots. Project recipes live in each project's `.vela/task-recipes.json` and team templates in `.vela/team-task-recipes.json`; both are plain files that can be shared through Git like other project files, and neither includes personal run history. Development builds default to `~/.vela-dev` and can copy conversations from `~/.vela` through Settings → Developer tools.

The macOS build is not notarized. If macOS blocks first launch, use **Open Anyway** in System Settings → Privacy & Security.
