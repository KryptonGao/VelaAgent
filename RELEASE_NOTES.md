# Vela 0.1.6

This release connects Vela to external tools and automation. Connect MCP servers from global or trusted project configuration, authorize Notion from Settings → Integrations, and schedule reminders or recurring agent work that runs in its own conversation. The embedded Pi SDK moves to exact 1.0.0, and MCP calls join the existing Ask / Smart / Full permission policy with a dedicated approval.

## New

- **MCP servers**: connect stdio and Streamable HTTP Model Context Protocol servers from `~/.vela/mcp.json` or a trusted project's `.pi/mcp.json`, with same-name project overrides, OAuth login through the system browser, and per-server enable, reconnect, and diagnostics in Settings → MCP servers. Tools default to deferred discovery through `tool_search` and can be switched to direct or hidden; `codemode` entries are normalized to deferred and Codemode stays off.
  - Project configurations require an explicit trust review bound to the workspace's real path and exact file content, and are not started until trusted. Credentials, logs, trust, and read-only grants live in the Vela data directory and follow `VELA_USER_DATA`; Vela does not read or migrate a user's global Pi configuration.
  - Users can confirm individual tools as read-only; the server's `readOnlyHint` is only a hint. Grants bind to the workspace, effective server configuration, and raw tool definition, and expire when any of them change. Plan and explore only receive explicitly confirmed read-only MCP tools plus resource listing and reading tools; other MCP tools stay hidden and are rejected again at execution time.
  - Non-read-only MCP calls follow the existing Ask / Smart / Full policy with a dedicated approval kind that shows the server, tool, and redacted parameters. MCP verdicts are never cached across calls, failures request approval, failed calls are not retried automatically, and non-read-only calls invalidate Goal validation and count as potential general-subagent mutations.
  - Root, general, and explore sessions each own an MCP extension instance while sharing credentials. Idle sessions reload immediately after configuration changes; running sessions show a pending-apply state and reload when idle. Disabling, deleting, revoking trust, or revoking a read-only grant blocks further calls immediately and cancels in-flight work. MCP calls appear in the existing tool cards, Trace, history, and usage counts with their server identity. See [MCP servers](docs/mcp.md).
- **Built-in integrations**: Settings → Integrations (设置 → 集成) connects built-in apps in one click, without URL, token, or JSON. Notion is the first integration: **Connect** opens the system browser for OAuth (PKCE, dynamic client registration when offered, localhost callback), with **Cancel** while connecting, **Disconnect**, and retryable error states; a login waits up to five minutes and cancellation closes the callback listener. The connection is global to the current Vela data directory and shared by every workspace and session; tools register as `mcp__builtin_notion__<tool>` under the same deferred discovery, approval, read-only filtering, and redaction as other MCP servers. Credentials are encrypted with the operating system's key store through Electron `safeStorage` in `integrations-auth.enc.json` and never fall back to plaintext; `integrations.json` stores only enabled plugin IDs. Current boundaries: one global account per plugin, Disconnect deletes local credentials without calling the provider's revocation endpoint, and a provider that requires a confidential client secret needs host-side provisioning. See [built-in MCP plugins](docs/built-in-mcp-plugins.md).
- **Scheduled tasks**: the sidebar's **Scheduled tasks / 定时任务** entry opens a dedicated page above **New conversation** where tasks can be created, edited, paused and resumed, deleted, and run immediately, with an execution history that opens the conversation each run produced. Tasks can also be created from chat: "remind me to review English every day at 10pm" makes the agent call `create_scheduled_task`, and `list_scheduled_tasks`, `update_scheduled_task`, and `delete_scheduled_task` manage existing tasks; Plan mode keeps the read-only listing. Agent tools are scoped to the calling conversation's workspace, while the page manages every workspace.
  - Schedules support one-time ISO 8601 times with a timezone, daily `HH:mm` with an IANA timezone, weekly times with weekday lists (0 is Sunday), and five-field cron expressions such as `0 22 * * *`, computed with `cron-parser` and correct across daylight-saving changes. Each task can pin its own execution mode (Ask / Smart / Full), model, and reasoning effort, or follow the application settings; an explicitly selected model that is unavailable is recorded as a failure instead of silently falling back. Task settings apply to scheduled and immediate runs and never change the current conversation or the application defaults, and the task's permission mode covers its file, terminal, browser, and MCP tools plus its subagents.
  - Each run creates and persists its own conversation in the task's workspace and executes through the normal agent prompt in Agent mode, without switching the conversation or workspace the user is viewing. The Electron main process owns the scheduler with a nearest-deadline timer, reconciles system time at least every 30 seconds, follows `powerMonitor` suspend and resume, and keeps running after windows close on macOS while Vela is open; quitting stops it. At most one run per task executes at a time: a duplicate **Run now** is rejected, a scheduled tick whose previous run is still active is recorded as skipped and the schedule advances, pausing stops future runs only, a running task cannot be deleted, and an expired one-time task must be edited to a future time first.
  - Nothing runs while the application is closed or the computer is asleep. The default `run-once` policy merges a backlog into a single catch-up run and then computes the next time, `skip` drops runs more than 60 seconds late, and one-time tasks complete when triggered or skipped. Tasks and records live in `scheduled-tasks.json` in the Vela data directory and are replaced atomically; every change saves the running record and the advanced next time before creating the conversation and running the prompt, and each task keeps its last 100 finished records. A normal quit marks an in-flight run as interrupted, and a `running` record left by an unexpected exit also becomes interrupted on the next start with its conversation ID preserved and no automatic replay. See [scheduled tasks](docs/scheduled-tasks.md).

## Improved

- The embedded Pi SDK is upgraded from 0.87.1 to exact 1.0.0 across all workspaces, including an MCP extension patch bound to that exact version. Existing tools, modes, and session data are preserved, and version 3 sessions written by 0.87.1 still open. Running input now distinguishes queued input from input handled by extensions, the existing OpenAI API-key and OpenAI Codex login flows are retained, and Pi 1.0 classifier-only providers stay out of Vela's chat model catalog. Codemode, virtual models, classifiers, and image generation remain outside this migration. See [migration validation](docs/pi-1.0-migration.md).
- Settings → MCP servers supports form-based editing and JSON import, shows configuration sources and project overrides, connection status, tool counts, per-tool details, and redacted diagnostics, and runs OAuth login in the system browser with cancel and retry.
- A child agent session now disposes through the runtime when the agent ends, releasing its MCP instance and resources with it; general subagents' MCP calls are also recognized as workspace mutations for Git refresh and Goal validation.

## Upgrade

Quit Vela completely, replace the application with this version, and reopen it. Keep your existing `~/.vela` directory (or the directory specified by `VELA_USER_DATA`); no data reset is needed. Existing sessions, model accounts, workspaces, browser cookies, and site storage continue to work.

New state lives in the Vela data directory: MCP configuration, credentials, and policy files (`mcp.json`, `mcp-auth.json`, `mcp-policy.json`, `mcp.log`), integrations (`integrations.json`, `integrations-auth.enc.json`), and scheduled tasks (`scheduled-tasks.json`). Vela does not read or migrate MCP configuration from a local Pi installation; add servers in Settings → MCP servers or in `~/.vela/mcp.json`.

The macOS build is not notarized. If macOS blocks first launch, use **Open Anyway** in System Settings → Privacy & Security.
