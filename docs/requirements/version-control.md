本文记录目标行为、功能范围和验收标准；第 2 节的实现基线是需求整理时的现状，P0 实现完成后以代码和测试为准。

## 1. 产品目标与已确定方向

在「对话」「轨迹」之后新增「版本控制」标签页，英文为 `Version Control`，让用户在同一窗口完成以下工作流：

**审阅改动 → 暂存 → Commit → Push → 创建 PR → 跟进检查与审阅。**

已确定的产品方向：

- 首期包含 Commit、Push、原生 PR 创建，以及 Fetch、基础 Pull 和分支操作。
- 历史页默认使用提交关系图，展示提交、分支轨道和合并关系，参考本次讨论中用户提供的图表。
- Commit Message、PR 标题与描述支持 AI 生成、润色和重新生成，结果可编辑。
- GitHub 集成统一通过 GH CLI；本地版本控制通过 Git CLI；AI 文案调用 Vela 已配置的模型。
- 本地 Git 功能不依赖 GitHub 登录，也不依赖 AI 模型可用。
- 正常的用户显式操作直接执行并反馈；破坏性操作展示具体影响范围，不为常规操作增加重复确认。

主要使用者是正在通过 Vela 开发和审阅代码的个人开发者及团队成员。首期以当前工作区为中心，不承担完整 GitHub 项目管理工具的职责。

现有模型需要补足的表达能力：

- `GitFileChange.staged` 仅为布尔值；同一文件同时存在索引和工作区改动时，`parseEntry` 将其归为未暂存。目标模型必须分别表达两部分内容。
- 当前 `collectStatus` 未覆盖未合并文件记录，目标模型必须表达冲突状态。
- 当前 PR 查询可能将命令非零退出视为没有 PR，目标行为必须区分无 PR、认证失败、网络失败和读取失败。
- 当前远程信息主要围绕 `origin`，目标行为必须明确实际操作的远程与 PR 目标仓库。

## 4. 信息架构与布局

### 4.1 一级标签与上下文

需求 ID：`UI-01`，级别：P0。本小节覆盖标签入口及工作区语义。

一级标签为 `对话 | 轨迹 | 版本控制`。默认仍进入对话，切换视图不停止 Agent 执行。

版本控制页显示当前聊天对应工作区的实时状态，不是该聊天发生时的历史快照。顶部始终明确显示实际工作区或 worktree；同一工作区被多个聊天使用时共享 Git 状态。

没有聊天但已选工作区时，也可以进入版本控制页。没有模型时仍可手工使用本地 Git 功能。

### 4.2 公共工具栏

需求 ID：`UI-02`，级别：P0。

- 仓库名称、实际工作目录、当前分支或 Detached HEAD 状态。
- upstream、待推送/待拉取提交数；无 upstream 时显示「尚未发布分支」。
- 分支选择、Fetch、Pull、Push/发布分支、当前 PR 入口。
- 最后一次成功 Fetch 的时间；本地状态刷新与远程 Fetch 是不同操作。
- Git/gh/认证状态按需要展开，不让配置提示占据正常工作流。

### 4.3 二级页面

需求 ID：`UI-03`，级别：P0。本小节同时覆盖右侧变更面板共享状态及窄窗口布局。

| 页面 | 布局与主要任务 |
| --- | --- |
| 改动，默认页面 | 左侧文件列表，右侧 Diff，底部 Commit 编辑区 |
| 历史 | 左侧提交关系图及列表，右侧选中提交的元信息、文件列表和 Diff |
| Pull Request | 无 PR 时显示创建表单；已有 PR 时显示详情、检查及审阅摘要 |

版本控制页沿用现有主题、字体、图标和组件风格。窄窗口使用列表/详情切换，避免压缩成不可读的多列布局。

保留右侧现有「变更」工作面板作为对话中的快速审阅入口；与版本控制页共享状态与操作。用户在一处暂存后，另一处应同步更新。浮动环境卡片不得遮挡版本控制页的操作与内容。

### 4.4 状态保留与运行反馈

需求 ID：`UI-04`，级别：P0。

- 返回页面恢复选中项、滚动位置和筛选；数据失效时刷新，不展示上一工作区的旧结果。
- 生成和执行期间显示进行中状态，禁止同一动作重复提交。
- Agent 执行期间仍能查看 Diff、历史与 PR；提供运行状态、停止及返回对话入口。
- 存在审批或问题待回答时，显示入口引导回对话，不因切标签页遗漏交互。
- 图标按钮具备名称、键盘焦点及状态反馈；状态不能只依靠颜色表达。

## 5. 改动与暂存需求

本节 `VC-01–VC-07` 均为 P0。后续 `VC-15–VC-17` 见第 3.4 节。

| ID | 需求 |
| --- | --- |
| VC-01 | 文件按未暂存、已暂存分组；新增、修改、删除、重命名、未跟踪、冲突有明确文字或图标 |
| VC-02 | 同一文件同时有索引与工作区改动时，在两组分别出现，点击展示对应 Diff |
| VC-03 | 支持单文件、选中文件、全部文件暂存；取消暂存支持同样范围 |

普通提交严格使用索引内容，不根据文件列表上的选中状态猜测提交范围。

## 6. Commit 需求

### 6.1 表单与提交

需求 ID：`CT-01`，级别：P0。

- 标题必填，正文可选；显示当前作者身份及实际提交文件数、变更统计。
- 主按钮为「提交已暂存改动」。暂存区为空时禁用，并说明原因。
- 提供独立的「全部暂存并提交」，先展示将包含的文件，不隐含包含忽略文件。
- 保留项目配置的 Git hooks 和提交签名行为，不默认跳过。
- 身份缺失时说明需配置的姓名/邮箱，提供显式配置入口；不自动覆盖全局 Git 配置。
- 成功后显示短 SHA，可打开历史详情或继续 Push；清理已成功使用的提交草稿。
- 失败时保留草稿并刷新真实状态。Hook 可能改变文件或索引，不能假设失败后内容完全不变。
- Hook 或签名过程需有可见输出/处理指引，不能在隐藏交互提示上无限等待。
- Detached HEAD、冲突、进行中的 Merge/Rebase/Cherry-pick 等场景，首期限制普通提交流程并提供处理入口。

### 6.2 Commit 并 Push

需求 ID：`CT-02`，级别：P0。

用户一次点击明确授权两个步骤，界面分别显示 Commit 与 Push 状态。Commit 成功而 Push 失败时，本地提交保留，恢复入口只重试 Push，不能重新 Commit。

仅点 Commit 不隐含 Push。已有待推送提交但没有新暂存内容时，提供独立 Push 入口。

### 6.3 草稿

需求 ID：`CT-03`，级别：P0。PR 创建草稿保存归入 `PR-02`。

Commit 草稿按实际工作树与分支保存，重启后恢复；Detached HEAD 的草稿按提交定位。不同聊天共享同一工作树和分支时使用同一草稿，并显示内容更新，不产生相互覆盖的独立草稿。

## 7. Fetch、Pull、Push 与分支

### 7.1 同步行为

本小节 `VC-08–VC-14` 均为 P0；高级同步需求 `SY-01–SY-05` 见第 3.4 节。

| ID | 需求 |
| --- | --- |
| VC-08 | Fetch 显示所选远程、进度、结果和更新时间；失败保留上次成功的数据并标记过期 |
| VC-09 | Pull 首期显式采用仅快进策略；分叉时停止并解释原因，不自动改用 Merge 或 Rebase |
| VC-10 | Pull 首期要求工作树及索引干净；否则提示先提交、通过终端保存到 Stash 或处理改动，不自动 Stash |
| VC-11 | Push 显示远程、目标分支及待推送提交；第一次发布允许选择远程和目标分支，并建立 upstream |
| VC-12 | 已有 upstream 时据其确定默认目标，不将所有操作硬编码到 origin |
| VC-13 | 推送拒绝区分网络、认证、权限、保护规则和远程变化；提供具体恢复动作，不自动强推 |
| VC-14 | 请求超时或取消后重新核对实际结果，显示成功/失败/结果待确认，不仅根据进程退出判断是否产生变更 |

ahead/behind 相对于本地已获取的远程引用计算；没有 upstream 时不标记为「已同步」。Push 前刷新目标远程信息并核对目标与提交范围。

### 7.2 分支操作

需求 ID：`BR-01`，级别：P0。下文的远程配置界面为 P1 的 `SY-01`；后续分支增强见 `BR-02–BR-04`。

- 搜索本地/远程分支，标记当前分支、upstream，以及已被其他 worktree 检出的分支。
- 创建分支默认基于当前提交；从远程分支建立本地跟踪分支时明确两者关系。
- 切换前提示未提交改动是否会随切换保留；遇到会覆盖改动或其他 worktree 占用时停止，不强制切换。
- 首期无远程时提供 Git 远程配置指引；完整添加/编辑/删除远程的界面属于 P1。

## 8. 提交关系图（Commit Graph）

### 8.1 图表语义

需求 ID：`CG-01`，级别：P0。

| 元素 | 需求 |
| --- | --- |
| 节点 | 一个节点对应一个提交；选中状态清晰，与 HEAD 标记区分 |
| 边 | 表示提交与父提交的关系；Merge 显示全部父提交，不只展示第一父提交 |
| 轨道 | 使用不同颜色辅助追踪；颜色不代表作者或永久的分支身份 |
| 引用 | 显示 HEAD、本地分支、远程分支、Tag；引用过多时折叠并可展开 |
| 行内容 | 默认显示标题、短 SHA、作者和时间；完整标题可展开或在详情查看 |
| 未推送状态 | 标记相对 upstream 的待推送提交；无 upstream 单独标记未发布 |

分支名称只出现在相应引用位置，不能将已经没有引用的历史轨道虚构成仍存在的分支。

### 8.2 查询、分页与搜索

需求 ID：`CG-02`，级别：P0。

- 默认范围为当前分支，支持全部本地已知分支；远程历史以最近 Fetch 的内容为准。
- 保持拓扑关系的排序，避免按显示时间独立排序导致父子连线错误。
- 首期建议每批 100 条，按需加载；大仓库不能一次读取/渲染完整历史。
- 分页在同一历史快照上延续；HEAD 或引用变化时提示刷新或重新建立快照，避免漏项、重复和错连。
- 页尾未加载父节点保留延续标记；浅克隆缺失历史标记为边界，不能画成确定的根提交。
- 图表支持定位 HEAD、选中提交和指定分支引用。
- 搜索标题、SHA、作者，覆盖选定范围而不只覆盖已渲染页面；结果分页展示，选择结果后定位并加载上下文。
- 默认高亮命中并保留关系。若提供仅显示结果的列表，必须说明其不是完整拓扑图。

### 8.3 提交详情与交互

需求 ID：`CG-03`，级别：P0。后续历史操作 `HI-01–HI-06` 分别归属 P1/P2/P3，见第 3.4 节。

- 展示完整 Message、SHA、作者/提交者、各自时间、父提交及引用。
- 展示该次提交的文件列表和 Diff；普通提交相对父提交，根提交相对空树。
- Merge 默认相对第一父提交展示，并明确对比依据；支持切换其他父提交。
- 支持复制 SHA、复制 Message、打开当前文件；文件当前不存在时说明，不假装打开历史版本。
- 保留滚动和选择；图表绘制不能依赖终端 ASCII 图的屏幕位置解析，应使用结构化提交和父节点数据。
- 首期不开放历史改写类右键动作；后续新增操作仍需显示实际影响范围。

## 9. Pull Request 需求

### 9.1 创建表单

需求 ID：`PR-01`，级别：P0。

| 字段 | 需求 |
| --- | --- |
| 目标仓库 / base | 从实际远程和仓库信息推导并允许修改；识别失败时要求选择，不能默认为 main 后静默创建 |
| 来源仓库 / head | 显示实际来源及分支；首期优先完成同一仓库的分支工作流 |
| 标题 / 描述 | 可手写、AI 生成与润色，支持 Markdown 预览 |
| 模板 | 识别仓库 PR 模板；多个模板时让用户选择，保留结构 |
| Draft | 提供「创建草稿 PR」与「创建 PR」两个明确动作 |
| 范围预览 | 显示相对选定 base 的提交与文件差异，明确包含哪些尚未推送的提交 |

PR 范围应与 GitHub 的分支比较语义一致，依据选定 base 与 head 的共同祖先及 head 变化确定；不能用工作区未提交 Diff 或只取最后一个提交替代。

### 9.2 创建流程

需求 ID：`PR-02`，级别：P0。本小节包含创建草稿保存、结果核对及聊天关联；后续 fork 与 Enterprise 支持分别为 `SY-02`（P1）、`SY-05`（P3）。

1. 核对工作区、仓库、分支及用户输入，查询是否已有相同来源/目标的未关闭 PR。
2. 来源尚未推送时，明确展示「Push → 创建 PR」两个步骤和推送目标；用户点击对应组合动作才执行。
3. 确认目标范围非空，实际 PR head 与用户预览一致。
4. 通过 GH CLI 创建，成功后显示 PR 编号、URL、状态，并保存当前聊天与 PR 的关联。
5. 创建失败保留草稿；结果不明时查询远端，确认未创建后才重试，避免重复 PR。

已有 PR 时跳转已有详情；已关闭或已合并的 PR 单独显示，不误判为可继续更新的当前开放 PR。不让 `gh` 的交互提示隐含决定推送、创建 fork 或选择仓库。

首期只要求展示并打开已有 PR，编辑远程 PR 的原生表单属于 P1。复杂 fork 或 Enterprise 场景暂不支持时明确提示，并提供网页/终端入口，不能构造错误的 github.com URL。

### 9.3 详情、检查与刷新

需求 ID：`PR-03`，级别：P0。合并约束归入 `PR-07`（P2），不计入 P0 的执行能力。

- 展示编号、标题、描述、URL、base/head、Draft/Open/Merged/Closed、审阅结论与检查摘要。
- 检查列表区分通过、失败、等待、跳过、取消和无检查，提供详细页面链接。
- 审阅结果不能把过期批准或被新审阅取代的结果当作当前批准。
- 首期支持手动刷新、重新进入页面刷新及 Push 后刷新；页面可见且 PR 开放时可进行有退避的后台更新，隐藏时停止常规轮询。
- 将「无 PR」「gh 不可用」「未登录」「权限不足」「离线」「读取失败」作为不同状态。
- P2 的 `PR-07` 合并功能必须依据 GitHub 当前规则及预期 head 核对，不凭检查通过或历史批准数量判断可合并。

## 10. AI 文案辅助

### 10.1 通用交互

本小节 `AI-01–AI-08` 均为 P0，并包含下文的独立请求约束。

| ID | 需求 |
| --- | --- |
| AI-01 | 空白表单提供「AI 生成」；已有文字提供「AI 润色」及重新生成 |
| AI-02 | 生成结果是可编辑草稿，不隐含 Commit、Push、创建/更新 PR 或执行命令 |
| AI-03 | 支持更简洁、补充原因、改变语言等调整指令；保留上一版，用户可选择采用 |
| AI-04 | 显示模型与输入范围，例如「依据已暂存的 4 个文件」或「依据 feature/login → main 的 6 个提交」 |
| AI-05 | 默认使用当前聊天选定模型；无聊天时使用用户配置的默认模型；无可用模型仅限制 AI 功能 |
| AI-06 | 支持取消、超时和重试；失败保留原文，用户开始编辑后到达的结果进入候选区，不能覆盖输入 |
| AI-07 | 输入内容按快照绑定工作区、分支、Diff 和选项；切换目标后旧结果不能填入新目标表单 |
| AI-08 | 数据变化后保留草稿并提示依据过期；不强制丢弃用户文案，提交/创建前另行核对实际操作范围 |

文案请求独立于 Agent 执行流程，不新增一轮聊天、不触发工具调用。生成区域显示会产生模型请求；不要求为每次生成增加额外审批。

### 10.2 Commit Message

需求 ID：`AI-09`，级别：P0。

输入以已暂存 Diff、文件状态和统计为事实依据；可补充当前任务目标、用户说明和近期提交标题。若选择「全部暂存并提交」准备模式，应先展示拟提交范围，并说明生成依据是拟暂存内容，不能标成实际索引。

输出为可分别编辑的标题与正文。格式和语言优先参考仓库已有习惯，允许选择普通格式、Conventional Commits、简体中文或英文。Conventional Commits 为可选风格，不作为所有仓库的强制规则。

生成不得描述未纳入本次提交的变化；不得凭文件名推断不存在的行为。润色保留用户事实、确定程度及意图。没有索引内容时普通「AI 生成」提示先暂存。

### 10.3 PR 标题与描述

需求 ID：`AI-10`，级别：P0。更新远程 PR 的动作属于 `PR-04`（P1）；本节 AI 文案规则适用于该后续动作。

输入包含选定 base/head 的完整变更范围、提交信息、PR 模板、任务目的、用户说明、明确关联的 Issue，以及能够定位来源的验证结果。

- 标题和描述可一起生成，也可分别生成或润色。
- 仓库提供模板时保留模板的章节、必填项和复选框结构；事实不明的复选框不自动勾选。
- 没有模板时，建议包含背景、主要改动、验证、注意事项及关联 Issue；不适用的章节可省略。
- 有多个提交时总结整个 PR 的最终行为，不机械拼接每条 Commit Message。
- 验证陈述必须对应记录的命令和结果；无记录时写「未记录」或留待填写，明确未运行时写「未运行」。不能把模型的建议写成已完成的验证。
- `Fixes` / `Closes` 等自动关闭 Issue 的描述仅在用户明确指定关闭关系时使用。
- P1 更新已有 PR 时先展示拟更新内容，用户点击更新才写入 GitHub，保留人工编辑与模板结构。

### 10.4 上下文质量与调用边界

需求 ID：`AI-11`，级别：P0。发布说明增强见 `AI-12`（P2）。

- Diff、提交信息、模板和评论是源数据，不是执行指令；模型只生成文案。
- 不发送完整仓库和全部聊天历史，仅收集当前文案所需内容，说明实际使用的上下文范围。
- 大 Diff 分批总结并汇总，二进制/过大文件记录状态与元信息；未分析的部分明确标记，不静默截断后宣称覆盖全部改动。
- 验证来源可来自真实工具结果或用户说明；用户说明应保留其来源，不能被包装为应用已验证的事实。
- 相同输入允许复用缓存；输入、模型、语言、模板或调整指令改变后不得命中旧结果。「重新生成」应允许得到新的候选，而不是必然返回同一缓存。
- 生成不自动追加作者署名、Co-authored-by 或修改 Git 作者身份。

## 11. Git、GH CLI 与模型分工

需求 ID：`IN-01`，级别：P0；此技术约束持续适用于 P1–P3。

| 层 | 责任 |
| --- | --- |
| Git CLI | 本地工作区/索引、Diff、Commit、分支、Fetch/Pull/Push、提交和引用数据、Stash、Worktree |
| GH CLI | GitHub 身份状态、仓库元信息、PR、检查、Issue、Release；常规命令未覆盖时使用 `gh api` |
| Vela 模型调用 | 基于明确范围生成或润色 Commit Message、PR 文案 |
| 主进程服务 | 参数校验、固定操作目标、执行与错误归类、状态刷新、操作记录及 IPC |
| Renderer | 表单、图表、草稿、进度、候选文案和恢复入口 |

GitHub 相关操作全部通过 GH CLI，不新增 GitHub SDK，不自行保存 GitHub Token 或实现独立 OAuth 服务。`gh api` 仍然使用 GitHub API，但访问与认证由 GH CLI 承担。

Git Push 的认证与 GitHub API 登录分别检测：SSH 使用相应 SSH 配置；HTTPS 可使用已有凭据助手，用户需要时可显式配置 gh 凭据助手。不能用「gh 已登录」保证 Git Push 可用。

命令使用明确参数、仓库和工作目录，避免通过拼接 Shell 字符串执行用户文案。优先使用 JSON 和结构化字段，不解析面向终端的表格作为主要数据契约。正文通过文件或标准输入传递，保留实际换行。

`gh pr create --fill` 仅复用提交信息，不作为 AI 文案实现。适配时需显式确定 base/head 和正文，避免 GH CLI 在隐藏的交互会话里自行选择推送或 fork。

## 12. 操作一致性与恢复

### 12.1 固定目标与并发

需求 ID：`OP-01`，级别：P0；目标与一致性规则持续适用于后续操作。

- 每个操作保存目标工作树、仓库、分支、预期 HEAD、远程或 PR 信息。异步过程不得在执行时重新读取全局当前工作区作为目标。
- 同一工作树的索引和文件变更串行执行；不同 worktree 共享引用或远程配置的动作还需按共同仓库协调。
- 应用内锁不代表外部 Git 进程被锁住；执行前后重新核对真实状态，识别 Git 锁冲突，不能自动删除外部锁文件。
- Agent 在同一工作树执行期间，首期阻止暂存、丢弃、Commit、切换分支、Pull 等影响其文件或索引的操作；仍可查看、生成文案和读取远程状态。
- Push 与 PR 创建依据已提交快照执行，执行前仍需核对 head 和范围；发现 Agent 或外部进程更新目标时刷新预览，不悄悄纳入新提交。
- 切换工作区后，旧操作结果进入原目标的记录，不更新新工作区表单。

### 12.2 操作记录

需求 ID：`OP-02`，级别：P0。后续记录检索与导航为 `OP-04`（P1）。

记录操作类型、目标工作树/分支、执行时间、步骤、结果、生成的 SHA/PR URL 及可读错误。操作记录按目标保存，可从当前聊天打开；重新启动后仍能看到关键结果。

成功、失败、部分完成、结果待确认分别显示。应用退出时未完成的操作，重启后核对实际状态，不能直接重放写操作。记录中不保存凭据或未经处理的敏感命令输出。

### 12.3 聊天回退

需求 ID：`OP-03`，级别：P0。

聊天回退与 Git 历史操作是不同能力。现有回退范围见根目录 [README](../../README.md)。

- 回退消息不会撤销索引、Commit、Push、PR 或 GitHub 评论。
- 回退后保留版本控制操作记录，并刷新文件、索引、HEAD、分支及 PR 状态。
- 已经对外发布的变更，应使用独立 Git/PR 动作处理，不提供含义模糊的「撤销全部」。

## 13. 首期空状态与异常状态

需求 ID：`ER-01`，级别：P0；新增功能沿用状态区分与恢复原则。

| 状态 | 页面行为 |
| --- | --- |
| 未选工作区 | 提供选择工作区入口 |
| 非 Git 仓库 | 说明当前目录不是仓库；初始化/克隆暂不作为首期必需功能 |
| Git 未安装或不可用 | 说明本地功能不可用并提供配置指引，不自动安装 |
| 空仓库 / 无初始提交 | 显示空历史，仍可暂存并创建首个提交 |
| 无远程 | 可本地 Commit，Push/PR 显示配置指引 |
| 无 upstream | 显示发布分支入口，不显示虚假的同步完成状态 |
| gh 不可用或未登录 | 本地 Git 继续可用，PR 提供配置指引及可用的网页入口 |
| 无模型 | 手工 Commit/PR 继续可用，AI 区显示选择模型入口 |
| Detached HEAD | 清晰标记并引导创建/切换分支；首期不允许普通发布或创建 PR |
| 冲突 / 进行中的 Git 操作 | 列出冲突与操作类型，提供终端处理及刷新入口 |
| PR 数据不可获取 | 保留最近数据并注明过期/失败，不能显示成「暂无 PR」 |
| 超时 / 取消 / 应用重启 | 检查实际结果；无法确认时显示待确认并提供查询入口 |

## 14. 各级别验收标准

以下为实现后的验收场景，本次需求文档编写不执行这些操作或测试。

实现中的取舍：

- Fixup/Squash 只处理线性历史：目标提交到 HEAD 之间存在合并提交时拒绝，并指向 P3 的交互式 Rebase（`HI-05`）。重写由 git 原生命令组合完成，不启动交互式编辑器，因此不需要 `GIT_SEQUENCE_EDITOR` 脚本；失败时 `git reset --hard` 回到操作前 HEAD，不留半成品。
- 提交整理只把已跟踪文件的未提交改动视为阻塞（与预览的 `dirty` 判定一致）；未跟踪文件由 git 自行判断是否冲突。
- Reflog 查询是只读的：可达性用 `git merge-base --is-ancestor` 判定，引用来自一次 `git for-each-ref`，不修改任何引用。
- 强推不使用 `--force`，`previewForcePush` 也不改动本地引用：`ls-remote` 只读远程，推送时由 `--force-with-lease` 再做一次原子校验。
- PR 合并的预期 head 由服务在每次读取 PR 时记录（`prHeads`），首次核对以当前 head 建立基线；过期批准不计入 `approvals`，也不进入 `canMerge` 判断。
- Release 通过 `gh api repos/<owner>/<repo>/releases` 一次读取，包含说明与状态；GitHub 未提供 `isLatest`，按已发布记录中最新一条推导。
- 发布说明沿用 `AI-11` 的调用边界：请求独立于聊天、不触发工具调用；模型输出不写回 GitHub，也不创建标签或发布。
- 新增操作类型（`revert`、`cherry-pick`、`history-rewrite`、`reflog-recover`、`force-push`、`tag`、`release`、`pr-review`、`pr-merge`）沿用 `OP-02` 的记录与恢复入口。
